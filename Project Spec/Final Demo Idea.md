# **OPTIMIZED PRODUCT DEMO — FINAL DESIGN SPECIFICATION**
> The Final Project demo should be like this
## **1\. DESIGN NORTH STAR**

### **Product experience statement**

The product should feel like a **behavioral operating system for software evolution**.

It does not primarily present itself as an AI coding assistant. The Coding Agent is one participant inside a larger governed lifecycle:

**Software has memory → memory is evidence-backed → evidence becomes governed behavioral knowledge → human intent defines permitted change → semantic impact is analyzed → verification is locked before coding → the Coding Agent proposes → an independent system investigates → behavioral differences become evidence → evidence drives repair → the repaired result is independently verified → certification binds implementation to evidence → verified knowledge becomes part of future software memory.**

This is the core experience to preserve across every interaction. The source establishes the same progression from Software Archaeology through Behavioral Constitution, change definition, impact analysis, pre-implementation verification, development, independent verification, behavioral delta, repair, certification, and continuing behavioral evolution.

### **Design objective**

The redesign should make the product feel:

* technically deep without appearing complicated for its own sake  
* evidence-first rather than AI-first  
* operational rather than presentational  
* trustworthy without appearing sterile  
* dense where expert information matters  
* calm where decisions matter  
* visually memorable specifically at major trust and discovery moments

### **Core mental model**

The judge should gradually internalize five nouns:

**Memory**  
What the software has historically done.

**Constitution**  
What behavior is governed.

**Intent**  
What the human wants changed and preserved.

**Evidence**  
What independent investigation actually establishes.

**Certificate**  
What has ultimately been proven.

Everything else is an interaction around those five concepts.

### **Primary narrative equation**

The product should visually reinforce this sequence:

**HISTORY → GOVERNANCE → INTENT → IMPACT → VERIFICATION → CHANGE → EVIDENCE → ALIGNMENT → CERTIFICATION → MEMORY**

### **Design rule**

The redesign must not make the product look like 21 separate applications.

The **eight tabs are navigational phases of one product**, and the 21 primary screens are operational workspaces inside those phases.

The user should always feel that the same system is accumulating state.

# **3\. GLOBAL DESIGN SYSTEM**

## **Design character**

The visual character should be:

**technical, restrained, precise, evidence-native, high-trust, modern, developer-oriented, and quietly cinematic at major state transitions.**

The product should not resemble:

* a consumer AI interface  
* a generic enterprise dashboard  
* a futuristic “AI command center”  
* a collection of colorful cards

The product should feel closer to an **instrument panel for inspecting reality**.

The visual hierarchy should communicate that claims and evidence are serious objects.

## **Visual principles**

### **Evidence has visual weight**

An evidence-backed claim should feel more substantial than a system-generated suggestion.

### **State is explicit**

Words such as:

**OBSERVED**

**PROTECTED**

**LOCKED**

**UNVERIFIED**

**VIOLATED**

**REPAIR REQUIRED**

**CERTIFIED**

should behave as meaningful system states, not decorative badges.

### **Negative states are not visually hidden**

The first candidate's failure must be visually prominent.

The product should be confident enough to show:

**20 / 21 passed**

and still make:

**1 critical behavioral finding**

the dominant narrative.

### **Relationships matter more than boxes**

Where the product is explaining causality, use spatial relationship, graph structure, comparison, sequence, and connected evidence rather than card collections.

---

## **COLOR SEMANTICS**

Color must encode meaning consistently throughout the product.

| Semantic role | Visual meaning |
| ----- | ----- |
| Neutral | normal software/system context |
| Active accent | current navigation or user focus |
| Protected | governed behavior |
| Warning | suspicious, uncertain, or needs review |
| Critical | violation, dangerous behavioral change, or severe risk |
| Success | verified/preserved/certified |
| Muted | historical/contextual information |
| Locked | immutable downstream contract/state |
| Unverified | proposed but not trusted |

### **Specific semantic rule**

**Critical** should be reserved for genuinely consequential behavioral states.

Do not color every risk.

For example:

* `CACHE-041` as OBSERVED should remain visually quiet.  
* `AUTH-017` as CRITICAL / PROTECTED should be visually strong.  
* `Ghost #221` discovering 403 → 200 should use the critical semantic treatment.  
* a certified result should use a restrained success treatment, not celebratory decoration.

---

## **TYPOGRAPHY**

### **Application/navigation text**

Compact, highly legible, low visual emphasis.

### **Workspace title**

Strong but not oversized.

### **Primary state**

Largest hierarchy inside the workspace when the state itself is the story.

Examples:

**NOT CERTIFIED**

**VIOLATED**

**REPAIR REQUIRED**

**CERTIFIED**

### **Claim**

High-contrast technical statement.

Example:

> Tenant isolation must never be violated.

### **Evidence**

Smaller, more structured, provenance-oriented.

### **Metadata**

Quiet but readable.

Examples:

`AUTH-017`

`Ghost #221`

`Change #184`

`SHA256: 8f21...91ab`

### **System events**

Compact monospace or code-adjacent treatment where appropriate.

### **Technical identifiers**

Consistently distinguish machine identifiers from human labels.

---

## **ICONOGRAPHY**

Icons are functional.

Use them primarily for:

* state  
* relationship  
* direction  
* evidence type  
* execution  
* navigation

Evidence types should be distinguishable through icon \+ label rather than icon alone.

Do not use decorative iconography.

---

## **MOTION & TRANSITIONS**

Motion should answer one question:

> **What changed?**

### **Meaningful motion**

* Archaeology expands through evidence layers as the system discovers them.  
* Knowledge Graph nodes reveal connected behavior when selected.  
* Intent becomes visually “locked” when confirmed.  
* Semantic impact expands from the changed capability into affected behaviors.  
* Verification transitions across independent modules.  
* A critical behavioral difference surfaces from the evidence stream.  
* Repair moves the workflow backward into development without erasing the original evidence.  
* Re-verification resolves the previous contradiction.  
* Certification transitions the object from candidate to verified artifact.  
* Continuous evolution visually connects certification back into future memory.

### **Motion that should not exist**

Do not animate:

* every metric  
* every card  
* every status  
* every graph node constantly  
* generic spinners as primary storytelling  
* decorative particle effects

# **4\. PERSISTENT APPLICATION SHELL**

The application shell should maintain continuity without repeating large blocks of context.

## **Persistent left navigation**

The eight tabs remain visible throughout the experience:

**Discover · Govern · Define · Analyze · Develop · Verify · Decide · Certify**

Current tab is visually active.

Future tabs can appear available but not actionable until prerequisites are satisfied.

The navigation should therefore communicate progression, not merely location.

## **Persistent top context bar**

The application should maintain a compact context strip containing:

**Project**

`Payments API`

**Repository**

`github.com/acme/payments`

**Change**

`#184`

**Constitution**

`v1.0 ACTIVE`

**Current trust state**

Examples:

`NOT CERTIFIED`

`INDEPENDENT VERIFICATION`

`CERTIFIED`

Only the values relevant to the current stage should be emphasized.

## **Persistent workflow state**

A compact progression indicator should show:

**Discover → Govern → Define → Analyze → Develop → Verify → Decide → Certify**

The current stage is emphasized.

Completed stages appear completed.

Locked stages are visibly immutable rather than unavailable without explanation.

## **Trust state**

The application should maintain one persistent conceptual label:

**TRUST STATUS**

Possible values:

* Historical  
* Observed  
* Protected  
* Intent Locked  
* Verification Locked  
* Candidate / Unverified  
* Independently Investigated  
* Repair Required  
* Re-verified  
* Certified

This is critical because the product's central proposition is about how trust changes over time.

## **Persistent evidence affordance**

Where evidence exists, a compact evidence affordance should remain accessible without consuming significant visual space.

This can open the contextual Evidence Inspector.

## **Global rule**

Never repeat the complete project/change summary on every page.

Context should persist structurally.

# **7\. INTERACTION & STATE MODEL**

## **Global state principles**

### **Every state must have an owner**

Examples:

* Constitution owns governance state.  
* Intent Ledger owns human intent.  
* Verification Plan owns verification contract.  
* Candidate Patch owns development output.  
* Independent Verification owns investigation evidence.  
* Behavioral Delta owns observed semantic differences.  
* Certificate owns certification state.

### **Immutable state**

The following states become immutable when locked:

**Behavioral Constitution**

**Intent Ledger**

**Semantic Impact Map**

**Verification Plan**

Once downstream work begins, those objects should not silently change.

### **Trust state**

A Candidate Patch can never move directly:

`Candidate → Certified`

It must pass:

`Candidate → Independent Investigation → Evidence → Intent Alignment → Certification`

### **Failure state**

Failure is not destructive.

The first candidate can be:

`Failed`

then:

`Repaired`

while its original failure remains:

`Preserved Historical Evidence`

### **Evidence state**

Evidence transitions should be:

`Collected → Linked → Interpreted → Claim-Level Assessment`

### **Certification state**

Certification transitions should be:

`Eligible → Certified → Machine-Verifiable → Active`

---

## **Interaction hierarchy**

### **Primary interaction**

Changes workflow or trust state.

### **Secondary interaction**

Opens contextual explanation.

### **Deep interaction**

Traverses evidence or technical detail.

The interface should never require multiple clicks merely to understand why a selected object exists.

---

## **State language**

Use precise states:

**RUNNING**

**READY**

**LOCKED**

**OBSERVED**

**PROTECTED**

**VIOLATED**

**UNEXPLAINED**

**UNAUTHORIZED**

**REPAIR REQUIRED**

**RE-VERIFICATION**

**CERTIFIED**

Avoid vague states such as:

“Almost there”

“AI is thinking”

“Magic complete”

## **6\. Development and verification require visibly different planes**

The interface should never make the Coding Agent's development environment and the verifier's environment look like the same authority domain.

The trust boundary must remain recognizable even when navigation changes.

## **7\. Verification modules are modules, not pages**

Static Analysis, Differential Execution, Ghost Replay, Metamorphic Testing, Adversarial Testing, and Mutation Testing are internal modules of the Verification Control Center.

Their details appear contextually.

## **8\. Ghosts are executable knowledge**

Ghosts must not be reduced to historical text summaries.

Where selected, the user should be able to inspect:

* event  
* input  
* state  
* dependency state  
* configuration  
* feature flags  
* environment  
* replay outcome

The source explicitly defines Ghosts in these terms.

## **9\. Evidence fusion must remain conceptually visible**

Do not simplify the evidence model into:

`PASS COUNT`

or:

`CONFIDENCE SCORE`

The system's value comes from evaluating evidence with claim authority, relevance, provenance, severity, and confidence.

## **10\. Behavioral Delta is not a duplicate of Verification**

Verification answers:

> **What did independent investigation establish?**

Behavioral Delta answers:

> **What behavior actually changed?**

Intent Alignment answers:

> **Was that change authorized?**

These must remain three distinct conceptual states even though they can occupy one integrated workspace.

## **11\. Repair does not mutate history**

When Candidate Patch \#2 succeeds:

Do not overwrite the Candidate Patch \#1 failure.

Preserve:

`F-183`

`Ghost #221`

`AUTH-017`

as historical evidence.

## **12\. The final certificate must be evidence-bound**

Do not implement a generic “certified” badge as the final artifact.

The certificate must remain attached to:

* change  
* commit  
* environment  
* dependencies  
* verification configuration  
* behavioral result

as established in the source.

## **13\. The final screen should return to the larger product model**

The user should not reach a dead-end success page.

The final state must expose that:

**certification produced new behavioral knowledge.**

That is what closes the software-evolution loop.

## **14\. Primary interactions only**

The live path should emphasize interactions that change meaning:

* Run Archaeology  
* select behavior  
* inspect provenance  
* traverse Knowledge Graph  
* open protected claim  
* Activate Constitution  
* submit Change  
* Confirm Intent  
* select blast-radius node  
* Lock Verification  
* inspect Candidate Patch  
* Start Verification  
* open critical finding  
* inspect evidence convergence  
* compare delta to intent  
* Generate Repair Package  
* Start Repair  
* inspect before/after  
* Preserve Failure  
* certify  
* View Certificate  
* Merge

Avoid unnecessary clicks whose only effect is navigation.

## **15\. Presentation discipline**

The implementation should resist the temptation to fill empty space with:

* extra metrics  
* decorative graphs  
* activity feeds  
* AI-generated explanations  
* arbitrary badges  
* repeated summaries  
* secondary dashboards

Every element must support one of four functions:

**Comprehension**

**Evidence**

**Trust**

**Narrative progression**

## **16\. Final implementation principle**

The implementation agent should repeatedly evaluate every new UI surface against one question:

> **Is this a distinct product moment, or is this an internal state of a stronger existing workspace?**

If it is an internal state:

**drawer, panel, inspector, nested view, contextual state, or inline detail.**

Do not create another page.

## **17\. Final product architecture**

The final implemented product should feel like:

**ONE SYSTEM**

with:

**EIGHT JOURNEY TABS**

containing:

**TWENTY-ONE PRIMARY PRODUCT MOMENTS**

supported by:

**CONTEXTUAL EVIDENCE, GRAPH, INSPECTOR, AND EXECUTION VIEWS**

rather than:

**A SEQUENCE OF DISCONNECTED SCREENS.**

The defining architectural loop is:

**Discover behavior**

→ **Govern behavior**

→ **Define intent**

→ **Analyze impact**

→ **Lock verification**

→ **Develop**

→ **Independently verify**

→ **Fuse evidence**

→ **Determine behavioral delta**

→ **Align with intent**

→ **Repair**

→ **Re-verify**

→ **Certify**

→ **Preserve memory**

→ **Evolve again**

That is the product experience the implementation should make visible.
